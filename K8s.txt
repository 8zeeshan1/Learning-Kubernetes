* Can I Force Pods Onto the Control Plane?
Yes, you can. While it is highly discouraged in production environments for security and stability reasons, 
there are scenarios where it is normal:

- Single-Node Clusters: If you are using local testing tools like Minikube, Docker Desktop, 
or kind (Kubernetes in Docker), you only have one node. In these setups, the cluster provisioning tool automatically 
removes the control plane taint so that your single node can act as both the master and the worker.

- Manual Override: A cluster administrator can manually remove the taint from the control plane node using a command like:
kubectl taint nodes <node-name> node-role.kubernetes.io/control-plane:NoSchedule-

Deleting the existing pod ==> 

How to Delete a Running Pod=>
To permanently delete a pod, you use the delete command followed by the resource type and its name.
For the Nginx pod you created earlier, the command is:
==> kubectl delete pod nginx
What happens behind the scenes:
Kubernetes doesn't just instantly kill the container. It sends a "graceful termination" signal (SIGTERM) to your application, 
giving it a default of 30 seconds to finish serving current requests and shut down cleanly. If it doesn't shut down in 30 seconds, 
Kubernetes forcefully kills it (SIGKILL).

Note: Because you created this pod using kubectl run, it is an "unmanaged" pod. Once you delete it, it is gone forever. If it had 
been created by a Deployment, Kubernetes would immediately spin up a replacement to maintain the desired state.

The problem Kubernetes solves
Without Kubernetes, you manually run containers, expose ports, restart crashes, and scale — impossible at scale. Kubernetes handles container orchestration: managing containers automatically across machines. Your job becomes declaring what you want; Kubernetes continuously makes it true.

Kubernetes objects — what they do and how they stack
Pod — the smallest unit. Usually 1 pod = 1 container. Pods are temporary — they die and get replaced. Their IPs change.
ReplicaSet — ensures the desired number of pods always exists. If a pod dies, it creates a new one. It tracks pods by label selectors, not creation history.
Deployment — manages ReplicaSets. Handles rolling updates, rollbacks, and scaling. Traffic never flows through a Deployment — it only manages pods.
Service — gives you a stable endpoint that never changes, even as pods come and go. It finds pods using label selectors and load-balances traffic across them.
HPA (Horizontal Pod Autoscaler) — watches metrics and tells Deployments to scale up/down.

Service internals — what it actually is
A Service is not a container. It is not a running process on a node. It's a virtual networking abstraction implemented as routing rules.
When you create a Service, the control plane stores its definition in ETCD. Then kube-proxy on every node reads that definition and creates iptables/ipvs rules. Traffic hits those rules and gets forwarded to the right pod. The Service "lives" as distributed rules across all nodes — not as any single running thing.
For NodePort specifically, Kubernetes opens the same port on every node. So if nodePort: 30001, then Node1:30001, Node2:30001, Node3:30001 all work — even if your pod only runs on Node2. kube-proxy handles forwarding internally.

Two completely separate flows
This is the most critical architectural concept. There are two flows that never mix:

The control plane never sleeps
It's not just active during cluster creation. It continuously:

Reconciles state — desired 3 replicas, actual 2? Creates one immediately.
Schedules new pods — when autoscaling triggers, when deployments are updated, when a node fails.
Monitors node health — if a node dies, pods are rescheduled elsewhere.
Manages rollouts/rollbacks — Deployment updates flow through the control plane.
Stores all state changes — everything goes through API server → ETCD.

The distinction is: the control plane handles management traffic constantly, but application traffic never touches it.

Que> In the cluster every namespace have their own nodes and control plane also or nodes and control plane are common inside the cluster for all ns?
Ans> Nodes and control plane are shared/common across all namespaces in a cluster.
🧠 Real architecture

      ├── Pods
