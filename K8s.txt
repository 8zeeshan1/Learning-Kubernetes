What happens behind the scenes:
Kubernetes doesn't just instantly kill the container. It sends a "graceful termination" signal (SIGTERM) to your application, 
giving it a default of 30 seconds to finish serving current requests and shut down cleanly. If it doesn't shut down in 30 seconds, 
Kubernetes forcefully kills it (SIGKILL).

Note: Because you created this pod using kubectl run, it is an "unmanaged" pod. Once you delete it, it is gone forever. If it had 
been created by a Deployment, Kubernetes would immediately spin up a replacement to maintain the desired state.

The problem Kubernetes solves
Without Kubernetes, you manually run containers, expose ports, restart crashes, and scale — impossible at scale. Kubernetes handles container orchestration: managing containers automatically across machines. Your job becomes declaring what you want; Kubernetes continuously makes it true.

Kubernetes objects — what they do and how they stack
Pod — the smallest unit. Usually 1 pod = 1 container. Pods are temporary — they die and get replaced. Their IPs change.
ReplicaSet — ensures the desired number of pods always exists. If a pod dies, it creates a new one. It tracks pods by label selectors, not creation history.
Deployment — manages ReplicaSets. Handles rolling updates, rollbacks, and scaling. Traffic never flows through a Deployment — it only manages pods.
Service — gives you a stable endpoint that never changes, even as pods come and go. It finds pods using label selectors and load-balances traffic across them.
HPA (Horizontal Pod Autoscaler) — watches metrics and tells Deployments to scale up/down.

Service internals — what it actually is
A Service is not a container. It is not a running process on a node. It's a virtual networking abstraction implemented as routing rules.
When you create a Service, the control plane stores its definition in ETCD. Then kube-proxy on every node reads that definition and creates iptables/ipvs rules. Traffic hits those rules and gets forwarded to the right pod. The Service "lives" as distributed rules across all nodes — not as any single running thing.
For NodePort specifically, Kubernetes opens the same port on every node. So if nodePort: 30001, then Node1:30001, Node2:30001, Node3:30001 all work — even if your pod only runs on Node2. kube-proxy handles forwarding internally.

Two completely separate flows
This is the most critical architectural concept. There are two flows that never mix:

Traffic bypasses the control plane, but metrics don't. This is a parallel, separate flow:

The control plane never sleeps
It's not just active during cluster creation. It continuously:

Reconciles state — desired 3 replicas, actual 2? Creates one immediately.
Schedules new pods — when autoscaling triggers, when deployments are updated, when a node fails.
Monitors node health — if a node dies, pods are rescheduled elsewhere.
Manages rollouts/rollbacks — Deployment updates flow through the control plane.
Stores all state changes — everything goes through API server → ETCD.

The distinction is: the control plane handles management traffic constantly, but application traffic never touches it.

DAY 11: MULTICONTAINER Pods

* Yes, we can have multiple containers inside a pod.
* Sometimes we need a dependency like we need one container to run only afte the another container, for example ther is an init container which
provides the inputs to the app container, so we want the app container only start after init container finishes processing the initial inputs,
and if the app container goes down init container goes down with it as well.
* Resources in the pods will be shared with all the containers.

# INIT CONTAINERS = These are the containers which runs before the main application container starts. It's job is to setup work and exit
then only the main container starts.
Example:
1. Setup database connection
2. Download config files
3. Wait for dependency
4. THEN start app
* If Init fails main container never starts.

apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    name: myapp-pod
spec:
  containers:
  - name: myapp-container
    image: busybox:1.28
    command: ['sh', '-c', 'echo Hello Kubernetes! && sleep 3600']
    env:
    - name: FIRST_NAME
      value: "Zeeshan"
  initContainers:
  - name: init-myservice
    image: busybox:1.28
    command: ['sh', '-c']
    args: ['until nslookup kubernetes.default.svc.cluster.local; do echo waiting for service to be up; sleep 2; done;']

* This is how we write the YAML for the multicontainer which is dependent on the initContainer the commands there it looks for the svc to be up
to start the main container otherwise it will be stuck in the middle.
* No matter how many initContainers are there in the pod they all have to satisfied and process first then only main container will run.

🧠 What are Workloads in Kubernetes?
A workload means:
Something that runs containers to perform work.
Kubernetes needs different ways to run applications because:
Not every app behaves the same.

Example:
Some apps should:
run forever
run once
run on every node
run on schedule

Different workload managers exist for these different needs.

🎯 Main Types of Workloads

1️⃣ Deployment
You already learned this.
Workload:
Long-running applications

Example:
Backend API
Frontend app
Auth service

Runs:
continuously
If pod dies:
recreate pod

2️⃣ DaemonSet
Workload:
One Pod on EVERY node
Purpose:
Run infrastructure/system services.

Example:
Monitoring agent
Log collector
Security scanner

Example:
Suppose cluster has:
Node1
Node2
Node3
DaemonSet creates:
1 Pod on Node1
1 Pod on Node2
1 Pod on Node3
Automatically.
Why?
Because some things must exist:
on every machine

Example:
Collect logs from every node.

3️⃣ Job
Workload:
Run task ONCE and finish
Unlike Deployment:
does NOT run forever

Examples:
Database migration
Generate report
Data processing
Backup

Flow:

Run Pod
      ↓
Task completes
      ↓
Pod exits
      ↓
SUCCESS

Example
Send monthly invoices

After work done:
container stops
No need to keep running.

4️⃣ CronJob
Workload:
Run task on schedule
Like Linux cron.

Examples:
Daily backup
Nightly cleanup
Every-hour report
Weekly email

Example:
Every day at 2 AM
Kubernetes automatically starts Job.

Mental Model-->
Deployment: Always running employee
DaemonSet: Security guard on every building floor (one on every node)
Job: One-time task worker
CronJob: Worker who comes every morning at fixed time

Big Picture Flow
Need always-running app?
      ↓
Deployment

Need pod on every node?
      ↓
DaemonSet

Need one-time work?
      ↓
Job

Need scheduled work?
      ↓
CronJob

One-line takeaway
Workload managers exist because different applications/tasks have different execution patterns—continuous, one-time, node-wide, or scheduled.

DAY 14: TAINT AND TOLERATIONS AND NODESELECTORS:

* When we want any node to take only specific pods to run on that node then we taint that node with some key : value so when the pod 
which don't have the same toleration for the node then that node would not be running on that node.

# SYNTAX OF TAINT: key=value:effect
# EXAMPLE: kubectl taint nodes <node name> gpu=true:noSchedule

* There are three typs of effects:
i. noSchedule: Do not Schedule new pods here.
ii. preferNoSchedule: Try not to place the pod here. It can still place a pod here if no place pod gets anywhere else.
iii. noExecute: all the old nodes will be evicted and only the new nodes with the toleration will be able to run here. if pod have toleration it
can stay and new pod with toleration can also be scheduled.

Que> Can we add more than one taint on a node?
Ans> Yes. A Kubernetes node can have multiple taints applied simultaneously.
Each taint is evaluated independently, and a pod must tolerate all relevant taints on a node to be 
scheduled there (unless filtered by effect semantics).
Example:
kubectl taint nodes node-1 env=prod:NoSchedule
kubectl taint nodes node-1 gpu=true:PreferNoSchedule
kubectl taint nodes node-1 dedicated=ml:NoExecute
This node now has 3 taints.

* NODESELECTORS: 
  It is the spec by which the pods select any specific node like they have the preference to which of the pods they will be preferring to run on.
  It looks for the specific labels which are applied on the nodes, in the pods we specify those labels and then scheduler looks for that labels
  only to up and run the pod on the node. When the labels matches pod gets scheduled on the specific node.

  Example: 
  spec:
  nodeSelector:
    env: production

DAY 15: NODE AFINITY

* NODEAFINITY:
  It is the advanced version of the NODESELECTORS. NodeSelector = Simple filter, NodeAfinity = Advanced Filter.
  NodeAfinity let's us write:
   -Rules,
   -Preference,
   -Multiple Conditions,
   -Soft Requirements,
   -Hard Requirements
  
  -There are two types of NodeAfinity:
   i.  requiredDuringSchedulingIgnoredDuringExecution  = This is the strict one if the pod doesn't find the node, pod won't schedule.
   ii. preferredDuringSchedulingIgnoredDuringExecution = This is linient one, if the pod doesn't find the proper node, it will shedule wherever it gets place.

  Example:
    spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: env
            operator: In
            values:
            - production

* Difference between NODEAFINITY and NODESELECTORS:

| Feature            | nodeSelector  | nodeAffinity |
| ------------------ | ------------  | ------------ |
| Exact match        | ✅            | ✅         |
| Multiple values    | ❌            | ✅         |
| Soft preference    | ❌            | ✅         |
| Advanced operators | ❌            | ✅         |
| Hard requirement   | ✅            | ✅         |
| Flexible logic     | ❌            | ✅         |

DAY 16: RESOURCE REQUESTS AND LIMITS

* Another service through which pods are scheduled on the particular nodes.
* Suppose we have nodes with limited cpu's and memories and all the nodes resources get's occupied by the different pods, now any pod comes 
  it will start throwing and error that insufficient resources and pod will not be scheduled. 
  So kubernetes keeps everything calculated like how much resources is used which pod is using how much, it keeps track of everything.

* There comes a situation where pod start taking more and more resources within the node,
  -because scheduler only sees the initially how much memory do a pod require to run and pod gets scheduled.
  -then after when the traffic increases the pod starts taking more and more cpu and memory and the situation comes where memory doesn't 
  left and pod gets crashed with OOM error (Out Of Memory error).
  -and then the node will also throw out that OOM pods. and node can crash too because of this

* So, to avaoid these things to happen we specify the request and limits to the pod so that when it takes more than specified resources the 
pod will be crashed and our node will be safe, healthy, up and running.

--> We can also specify the nameSpace inside the yaml file only.

* OOM Killed = It is the type of error occurs when the pod takes memory more than the limit memory, it is out of memory killed means pod killed
from the node.

* In Kubernetes, CrashLoopBackOff is a pod state indicating that a container starts, crashes, 
and Kubernetes repeatedly tries to restart it with increasing delays (“backoff”).

DAY 17: AUTOSCALING - VPA & HPA

* We do not monitor the deployment 24/7 so even though we have manual scaling option by increasing the replicas we can't just always do it 
maually so that is where the concept of pods autoscaling came in, so that more load can be handled without the application crash.

* HPA = Horizontal Pod Autoscaling-It is the autoscaling which increases the number of pods automatically in the node when the traffic increases.

* VPA = Vertical Pod Autoscaling-It is the the autoscaling in which the smaller pod is replaced by the bigger pod(more EC2 machines get added),
It comes with a downtime when the replacement of the pod is happening. so pod should be stateless and can afford the downtime.

* HPA only comes with the kubernetes inbuilt infrastructure other autoscalings like eventbased autoscalings and vpa we have to configure from
outside the kubernetes example: from AWS.

# METRIC SERVER => It is the service which keeps the track of the memory and cpu usage of the pods and how much memory and cpu is available.
It runs via pod inside the kube-system namespace and managed via deploy (metrics-server).
Kubelet on each node watches the CPU usage, RAM usage, container health and resource usage, Metric Server collects everything from the kubelets. 

To install it we need to execute an official command: kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

DAY 19: CONFIGMAPS 

* When we are giving environment variables to any of the pod's container we specify in it like 
env:
  - name:
    value:
but if in the same pod we need to give the same environment varibales to the another container then we will have to repeatedly write the environment
variables which is unnecessay and repeteation of task which can cause mistakes.
so we make a configmap defin env variables there and simply pass the reference to the containers so that once only we define the environments and 
can use anywhere inside the cluster.
We can refer to the configmap from any node or any pod whichever container needs the same environments we can give them the reference of configmap.

* QUE> Where does the ConfigMap actually live?
* ANS> A ConfigMap is stored in etcd, which is Kubernetes’ backing datastore.
      etcd stores the cluster state, including:
      Pods
      Deployments
      Services
      Secrets
      ConfigMaps
      StatefulSets
      RBAC rules
      etc.

* It is a good practice when we mount the configmaps with the volumes.
* If the list of the variables is too long we can give the --from-file=<pass the reference of the file> ex: app.config , instead of the --from-literal
we can write the key value pairs inside the file and give the reference of it. 

In the declarative way we can get the yaml file from the command kubectl create cm <name of cm> --from-literal=<key>=<value> -o yaml > my-config.yaml
This way we will be able to get the yaml file for the configmap and there in the data field we can add the key value pairs.
And in the pod if we don't want to specify again and again the keys we can directly give the file referece in 
 envFrom:
  configMapRef:                    
    name: my-config
And all my values will be applied in the pod.
