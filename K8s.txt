* Can I Force Pods Onto the Control Plane?
Yes, you can. While it is highly discouraged in production environments for security and stability reasons, 
there are scenarios where it is normal:

- Single-Node Clusters: If you are using local testing tools like Minikube, Docker Desktop, 
or kind (Kubernetes in Docker), you only have one node. In these setups, the cluster provisioning tool automatically 
removes the control plane taint so that your single node can act as both the master and the worker.

- Manual Override: A cluster administrator can manually remove the taint from the control plane node using a command like:
kubectl taint nodes <node-name> node-role.kubernetes.io/control-plane:NoSchedule-

So when the pod is created scheduler sees in which worker node it has to be reside in.--> kubectl get pods -o wide ==> 
We can see on which worker node the pod has been created.

Deleting the existing pod ==> 

How to Delete a Running Pod=>
To permanently delete a pod, you use the delete command followed by the resource type and its name.
For the Nginx pod you created earlier, the command is:
==> kubectl delete pod nginx
What happens behind the scenes:
Kubernetes doesn't just instantly kill the container. It sends a "graceful termination" signal (SIGTERM) to your application, 
giving it a default of 30 seconds to finish serving current requests and shut down cleanly. If it doesn't shut down in 30 seconds, 
Kubernetes forcefully kills it (SIGKILL).

Note: Because you created this pod using kubectl run, it is an "unmanaged" pod. Once you delete it, it is gone forever. If it had 
been created by a Deployment, Kubernetes would immediately spin up a replacement to maintain the desired state.

DAY 8
DEPLOYMENT AND REPLICATION

. Replication Controller

It spins up the replicas of the pod. It helps in spinning up the pod when it goes down. It spins up multiple
identical replicas of whatever number we set to replicate. (Refer SS)
Desired number of the pods up and running and maintained by the Replication controller all the time.

Replication Controller have the ability also to spin up the new nodes, suppose the pod needs to be replicated but the resources
of the node are over then replication controller will spin up the new node and will replicate the pod in that node.

For the replication control we need to give one more entry in the spec section that is template, we will define the template for 
telling the replication controller what kind of pod we want.

spec:
  template:
    metadata:
      name: nginx-pod
      labels:
        env: demo
        type: frontend
    spec:
      containers:
      - image: nginx
        name: nginx
  replicas: 3

If we want the details about the pod of the replication controller go on and run command=>
kubectl describe pod <pod-name>

. DEPLOYMENTS

Actually these ReplicaSets are not created by us these gets created by the Deployment resource.
Deployment manages the ReplicaSets and ReplicaSet manages the pods. (Refer SS)
Deployment is a higher level manager for the replica sets.
Deployment -> ReplicaSet -> pods
Deployment manages:
ReplicaSets
Pod versions
Rollouts: Gradually deploying new version of application.
RollBacks: Revert to previous stable version. 

Example:
current app: nginx:v1
we want: nginx:v2

without deployment: downtime possible and manual work will be required.
with deployment:
i.   It creates new ReplicaSet.
ii.  Gradually shifts the traffic.
iii. Delete old pods slowly.
iv.  Ensures app stays alive

=> kubectl get deploy --> to see what deployments do we have.
------- To see what are the objects in my cluster we can do ==> kubectl get all ---------
-> Changing the image version in the deployment:
   kubectl set <selector we have to set, ex: image> deploy/<name of the object> nginx=nginx:1.9.1
-> Describing the deployment:
   kubectl describe deploy <nginx-deploy>
-> RollOut history:
   kubectl rollout history deploy/<nginx-deploy>
-> RollBack:
   kubectl rollout undo deploy/<nginx-deploy>

DAY 9 : HOW DO WE MAKE THE APPLICATION AVAILABLE FOR THE OTHER USERS:

We will have different services which will interact with the pods and with the help of that we will be able to view the application.
Services will allow the communication between the pods.
We have various services:

. Cluster IP 
. Node port 
. External names
. Load balancers

i. Node Ports: 
  👉 NodePort exposes the application on the Node's port, not directly on your laptop OS port abstraction.
  BUT:
  👉 In local Kubernetes setups (kind/minikube/docker desktop), the node itself may actually be running inside Docker containers 
  or VMs, which creates another networking layer.
  Range for the node port is from 30000 - 32767.
  -> Types of ports:
    a) NodePort is something which get's exposed externally.
    b) target Port: It is the port on which the traffic gets redirected from the NodePort.
    c) port: internal service port: this will be the port which will be used by the services to communicate with the pods.

If we want to access the application from our localhost, from our machine, then we will have to make the cluster with
extraPortMappings inside it we will need to mention the containerPort the port on which the node container is listening
and will map it with hostPort which will be our localmachine port so this means on the hostPort we are making a request and 
on the containerPort container is making the node to listen to request and then pass it through the Node Port and then 
the request is passes from the service passway on the sercvice PORT where sercvice redirects request to the worker node's deployment
and deployment manages the pods and let us access the application.
